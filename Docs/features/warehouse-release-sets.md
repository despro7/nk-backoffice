# Комплектація та розукомплектування наборів (партійний облік)

Розділ `/warehouse/releases` — kit/unkit наборів у Dilovod з вибором партій компонентів, режимом коригування партійного обліку та автоматичним створенням kit-партій.

## Огляд змін (2026-10)

### Партійний облік (kit / unkit)

- Користувач обирає партії для кожного компонента набору (`ReleaseComponentBatchesPanel`).
- `componentBatches` передаються в preview/send; бекенд валідує через `validateReleaseBatches` (`server/modules/Warehouse/releaseBatchValidation.ts`).
- У `tpGoods` Dilovod payload додається `goodPart` для кожного рядка з партією.
- **Ручний вибір:** у drawer/списку доступні реальні `catalogs.goodParts` і віртуальні document-партії з балансу (для зведення). Для `documents.prodOrder` — бейдж «Без надходження» + `PRODUCTION_ORDER_BATCH_WARNING`.
- **Автопідстановка (звичайний kit / FIFO):** лише реальні `catalogs.goodParts` (`canSetTpGoodsGoodPart`). Якщо для компонента лише одна така партія — підставляється автоматично.
- Системні партії («Розукомплектування…», «Коригування обліку…») ховаються у звичайному kit (`isAutoGeneratedSystemBatch`); у correction mode залишаються.
- При `includeNonPositiveQty` (unkit крок 2) API доповнює balance-партії каталожними з `qty=0`.

### Редагування записів історії

- Спільне правило зі списанням/оприбуткуванням: `canEditWarehouseReleaseHistory` — власник + сьогодні (Київ), адмін без обмежень. Деталі: [`warehouse-writeoff-surplus.md`](warehouse-writeoff-surplus.md#редагування-історії).

### Kit-партія на виході

- Формат: `K` + YMMDD (`generateBatchSerialFromDate`, `formatKitBatchBaseName` у `shared/utils/kitBatchName.ts`).
- Перед send: `warehouseBatchesService.ensureKitOutputBatch` — шукає або створює партію з `code = K61003` для товару-набору.
- Створення через `DilovodGoodPartsService` → `saveObject` з `code`, `owner`, `date`, `expiration` (без `name`/`number` — див. `Docs/integrations/dilovod-metadata.md`).

### Режим «Коригування партійного обліку»

Switch у шапці сторінки. Двокроковий wizard:

1. **Крок 1 (correctionKit):** збір компонентів у тимчасовий інвентаризаційний набір `{sku}_rebatch`.
   - `POST /api/warehouse/releases/batch-correction/ensure-set` — створення/пошук набору у Dilovod.
   - `POST /api/warehouse/releases/batch-correction/fill-batches` — автозаповнення **усіма** партіями з позитивним залишком (реальні + віртуальні + системні) — виняток від звичайного правила «авто лише goodParts».
2. **Крок 2 (correctionUnkit):** розкладка з набору по цільових партіях; надлишок → нова партія «Коригування обліку {ДАТА}» через `createGoodPartBatch`.
   - `mergeNegativeBatchesForUnkit` також автопідставляє мінусові віртуальні document-партії (для зведення).

#### Пошук товарів у correction (2026-10-09)

- **Крок 1 (kit):** `SetSearchPanel` показує лише звичайні товари — без груп (`isGroup`), без комплектів (`set.length > 0`), без SKU `_rebatch`.
- **Крок 2 (unkit):** `GET /batch-correction/search-sets` → лише інвентаризаційні набори `_rebatch` (+ клієнтський `isRebatchSku`).

#### Детекція correction у історії (2026-10-09)

- `shared/utils/releaseBatchCorrection.ts` — `isReleaseBatchCorrection`: session UUID **або** коментар `Кор[еи]гування парт. обліку…` **або** SKU `_rebatch`.
- Перед `/send` у correction UI гарантує `correctionSessionId`; бекенд підставляє UUID, якщо в payload лише comment/rebatch.
- Чіп «Коригування» в `HistoryAccordionItem` більше не залежить лише від `correction_session_id`.

### Confirm-модалки

`ReleaseSendConfirmModal` + `releaseConfirmCopy.ts` — підтвердження перед:

- перемиканням kit/unkit;
- увімкненням/вимкненням correction;
- автозаповненням партій;
- створенням surplus-партії;
- видаленням рядка партії;
- фінальним send.

### Історія та архів

- `GET /api/warehouse/releases` — пагінація (`page`, `limit`, `status`).
- `ReleaseHistoryTab` — Pagination + Select статусу.
- `internalDocNumber` у `warehouse_release_set` (формат `K-{######}`, міграція `20261002180000_add_release_internal_doc_number`).

### Dry-run і preview

- `POST /releases/preview` — зведення з `componentBatches`, shortage/surplus, `kitOutputBatch`.
- `POST /releases/check-dilovod-batch` — перевірка наявності kit-партії в Dilovod.
- `GET /releases/last-kit-batches?setSku=` — партії з останнього комплектування для автопідбору при unkit.

### FIFO та заміна партій (2026-10-08)

- **FIFO:** кнопка в `ReleaseComponentBatchesPanel` → bulk `GET /api/warehouse/batch-numbers?skus=…` + `shared/utils/fifoBatchAllocation.ts` (`sortBatchesFifo`, `allocateBatchesFifo`). Старіші партії (за датою в номері / expiration) споживаються першими; при нестачі залишку — warning toast.
- **Prefetch:** при відкритті панелі компонентів (не correction) той самий bulk завантажує доступні партії для перевірки «чи є альтернатива на складі».
- **Заміна:** якщо позиція повністю укомплектована, але на складі є інші `batchId` — кнопка «Замінити партію» (одна лінія) або edit у рядку (кілька ліній) → `openDrawer` у режимі редагування індексу.
- **Dilovod:** bulk для FIFO/prefetch передає **`skipExpiration=true`** (див. також `Docs/features/warehouse-movement-mob.md`) — без десятків `getObject` по `header.expiration`. Сортування FIFO покладається на номер партії; drawer по одному SKU без `skipExpiration` лишає повний enrichment.
- **Кеш сервера:** ключ партій містить суфікс `exp` / `noexp`, щоб відповіді з/без термінів не змішувались.

### Історія, редагування, аудит (2026-10-08)

- **Редагування** запису в історії: лише **в день створення** (Europe/Kyiv) або роль **admin** — `shared/utils/releaseHistoryAccess.ts`.
- **Повтор send** для статусу `send_failed` — `retryFailedRelease` у `useReleaseSets.ts` (ті самі `componentBatches` з БД, якщо не передані з UI).
- **Аудит:** `WarehouseReleaseAuditService` → `hr_audit_log` (`entityType: warehouse_release_set`), `GET /api/warehouse/releases/:id/audit`, акордеон у `WarehouseReleaseAuditAccordion.tsx`.
- **Примітка Dilovod** при зміні полів історії — `warehouseReleaseRemark.ts` (`appendWarehouseReleaseDilovodRemark`).
- **Формат remark (2026-10-16):** оригінальний коментар зберігається; суфікс ` | Редакція → {хто}, {коли}` (без деталей diff). Повторне редагування замінює попередній суфікс (і legacy `Редаговано в backoffice…`). База — `dilovod_remark` після strip, інакше `comment` запису.
- **Проведення Dilovod (2026-10-16):** `syncWarehouseReleaseToDilovod` шле `saveType: 1` (REGISTER) + `posted: 1`, щоб edit не знімав проведення. `saveType: 2` лише при delete/`delMark`.

### Час операції — Europe/Kyiv (2026-10-16)

- Рядки `YYYY-MM-DD HH:mm:ss` без TZ парсяться/форматуються як wall-clock **Europe/Kyiv** (`shared/utils/kyivDateTime.ts`), незалежно від TZ Node-процесу.
- Інакше Dilovod отримував «локальний» час сервера, а звіти UI (`formatDate` / `operDate` з БД) показували +1 год (типово сервер UTC+2 vs Kyiv UTC+3).
- `formatDate` / `formatDateTime` на клієнті також з `timeZone: 'Europe/Kyiv'`.
- **Розширення (той самий день):** той самий контракт застосовано до переміщень, sale/return, writeoff/surplus UI, returns, cash-in/виписки — див. [`warehouse-movement-dilovod-export.md`](warehouse-movement-dilovod-export.md).

### Рефреш залишків при мета-змінах (2026-10-16)

- Зміна **дати / складу / фірми** перезапитує залишки набору (`availableQuantity` через `/stock-snapshot` + `asOfDate`) і партій компонентів (bulk batch-numbers).
- `batchStock` у вже обраних алокаціях **синхронізується** зі свіжим балансом (раніше писався лише якщо поле було порожнім).

### Kit-партія: колізії серійного номера

- `refineKitOutputBatchPlanForOccupiedCodes` у `kitBatchName.ts` — якщо запланований `K{YMMDD}` уже існує в Dilovod для іншого запису, план зсувається (suffix `-2`, `-3`, …) перед `ensureKitOutputBatch`.
- Пошук `findGoodPartsByOwnerIds` / `findGoodPartsByCodes`: Dilovod для `catalogs.goodParts` **не приймає** filter `IN` (`bad filter item`) — лише `=`. Інакше reuse існуючої `K-…` ламається (create → «партія вже існує»).

### Термін придатності комплекту

- ТП комплекту = `pickMinExpiration` по партіях компонентів (найстаріший).
- Якщо в **усіх** обраних партій компонентів немає ТП — модалка send запитує дату (`kitExpiration`); send без дати блокується.
- UI: HeroUI `DatePicker` + `I18nProvider locale="uk-UA"`; значення тримається як локальний `DateValue`, у батька йде YMD лише з 4-значним роком (щоб клавіатурний ввід не скидався через `parseDate`).

## Dilovod: обмеження `catalogs.goodParts`

У базі NK Food API **не** приймає `header.name` / `header.number` (ні при create, ні при update існуючого id). Канонічна назва партії — поле `code` (з префіксом `K` для kit). Деталі та live-приклади: `Docs/integrations/dilovod-metadata.md` → розділ `catalogs.goodParts`.

## Правила для агентів

1. Не хардкодити імена полів Dilovod — `dilovodMetadataService.getObject('catalogs.goodParts')`.
2. Kit-партія: `formatGoodPartCodeForDilovod` зберігає префікс `K`.
3. Валідація партій перед send — `validateReleaseBatches` з `requireBatches: true` для kit/unkit з явним вибором.
4. Correction surplus — ім'я «Коригування обліку {дата}», не плутати з kit `K{YMMDD}`.
